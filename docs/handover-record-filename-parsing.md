# 소송기록 파일명 파싱 핸드오버

## 목적

소송기록 폴더의 PDF 파일명을 `문서`, `서증`, `첨부서류`로 분류하고, 화면 표시명·당사자·정렬 순서를 만드는 현행 규칙을 다른 구현 또는 후속 작업자에게 전달한다.

이 문서는 현재 코드의 실제 동작을 기준으로 한다. 아래의 **현재 구현상 주의점**은 의도된 규칙이 아니라 후속 변경 시 결정을 내려야 할 한계다.

## 코드 위치와 영향 범위

- 파서 본체: [`src/renderer/src/viewer/recordOutline.ts`](../src/renderer/src/viewer/recordOutline.ts)
- 회귀 확인: [`scripts/verify-record-outline.mjs`](../scripts/verify-record-outline.mjs)
- 폴더 PDF 수집: [`src/main/index.ts`](../src/main/index.ts), [`src/main/remoteFs.ts`](../src/main/remoteFs.ts)
- 화면 연결: [`src/renderer/src/App.tsx`](../src/renderer/src/App.tsx)

`parseRecordFiles()`와 단일 합본 PDF의 `parseRecordOutline()`이 같은 `classify()`를 사용한다. 분류 규칙을 바꾸면 개별 PDF 파일명과 합본 PDF 북마크에 함께 적용된다.

## 입력 범위

- 선택한 소송기록 폴더 아래를 재귀 탐색한다.
- 숨김 파일·폴더는 제외한다.
- 확장자가 `.pdf`인 파일만 대소문자 구분 없이 처리한다.
- 로컬 탐색에는 깊이 제한이 없고, 원격 탐색은 최대 8단계 하위 폴더까지 처리한다.
- 파싱에는 전체 경로가 아니라 각 파일의 basename을 사용한다. 실제 파일 열기에는 원본 경로를 그대로 유지한다.
- 한글 파일명은 NFC로 정규화한 뒤 분석한다. 원본 파일명이나 경로는 변경하지 않는다.

## 권장 파일명 구조

파서는 모든 항목을 필수로 요구하지 않지만, 가장 안정적인 형식은 다음과 같다.

```text
[법원명_]사건번호_기록순번_제출일_문서종류_[상세정보]_[작성자].pdf
```

예시:

```text
서울중앙지방법원_2026가단12345_001_2026.07.20_소장_(대여금)_원고.pdf
2026비합50043_002_2026.06.30_서증_(을 제2호증의1 거래내역)_상대방.pdf
2025느합1050_013037_2025.08.13_준비서면_서증_입출금 자료_(을15-1_입출금 자료)_상대방.pdf
```

언더스코어(`_`)가 기본 토큰 구분자다. 다만 증거번호 안에서는 공백, `_`, 괄호, `-`, `–`, `—`, `의` 표기도 일부 허용한다.

## 공통 필드 추출

| 필드 | 현행 규칙 | 예시 |
|---|---|---|
| 법원 | 처음 발견한 `한글+법원` | `서울중앙지방법원` |
| 사건번호 | 처음 발견한 `연도 4자리 + 한글 1~5자 + 숫자 1~6자리` | `2026가단12345` |
| 제출일 | 표시용은 정확한 `YYYY.MM.DD`; 정렬용은 월·일 1~2자리와 점 뒤 공백도 허용 | `2026.07.20` |
| 기록순번 | 날짜 바로 앞 토큰을 우선하고, 없으면 세 번째 토큰을 사용; 숫자 1~6자리만 인정 | `001`, `013037` |
| 문서종류 | 날짜 다음 토큰; 날짜를 못 찾으면 세 번째 토큰; 모두 없으면 `문서` | `소장`, `준비서면` |
| 상세정보 | 최상위 ASCII 괄호 `(...)` 안의 첫 내용 | `대여금` |

법원과 사건번호는 폴더 전체에서 처음 매칭된 값 하나만 상단 사건 정보로 사용한다.

## 분류 우선순위

한 파일은 다음 순서로 한 범주에만 들어간다.

1. **서증**
   - `_`로 나눈 토큰 중 `서증` 또는 `서증서류`가 정확히 있거나,
   - 파일명에 `_서증_`이 있거나,
   - 아래 증거번호 형식이 발견되면 서증이다.
2. **첨부서류**
   - 서증이 아니면서 `_` 토큰 중 하나에 `첨부`가 포함되면 첨부서류다.
3. **문서**
   - 나머지는 모두 일반 문서다.

따라서 파일명에 `첨부`와 인식 가능한 갑·을 증거번호가 함께 있으면 서증이 우선한다.

## 증거번호 규칙

인식 대상은 `갑` 또는 `을`로 시작하는 번호다. 다음 형식은 같은 접두사로 정규화한다.

| 입력 예 | 정규화 결과 |
|---|---|
| `갑1`, `갑 제1호증`, `갑_1` | `갑1` |
| `을15-1`, `을15–1`, `을15—1` | `을15-1` |
| `을 제2의1호증`, `을 제2호증의1` | `을2-1` |

증거번호 앞에는 문자열 시작 또는 공백, `_`, 하이픈류, 여는 괄호가 있어야 한다. 번호 뒤에는 문자열 끝 또는 공백, `_`, 하이픈류, 괄호, 점, `의`가 와야 한다.

`호`와 `증`은 각각 선택 사항이므로 `갑 1`처럼 짧은 표기도 현재는 서증으로 인식한다.

## 표시명 생성

### 서증

기본 표시명은 `정규화된 증거번호 + 공백 2개 + 증거명`이다.

```text
갑1  입금내역
을2-1  거래내역
```

증거명은 다음 순서로 찾는다.

1. 괄호 안의 `갑 제1호증(문서명)`
2. 괄호 안의 `갑1_문서명` 또는 `갑1 문서명`
3. 괄호 내용에서 증거번호 접두사를 제거한 나머지
4. 파일명 본문에서 증거번호 뒤 구분자 다음의 나머지
5. 최상위 괄호가 둘 이상이면, `갑`·`을`이 없는 두 번째 괄호 내용

증거번호를 찾지 못했지만 `서증` 토큰으로 분류된 경우 표시명은 `서증`이다. 증거명은 2자 이상일 때만 붙인다.

### 첨부서류

- 첫 괄호 내용이 있고 그 내용에 `첨부`가 없으면: `날짜 | 괄호 내용`
- 그렇지 않으면: `날짜 | 문서종류`
- 날짜가 없으면 `날짜 | ` 부분은 생략한다.

### 일반 문서

- 기본: `날짜 | 문서종류`
- 첫 괄호 내용이 문서종류와 다르면: `날짜 | 문서종류 - 괄호 내용`
- 날짜가 없으면 `날짜 | ` 부분은 생략한다.

문서종류와 괄호 내용을 비교할 때는 NFC 정규화 후 공백, `_`, `-`, 괄호를 제거한다.

## 당사자 판정

| 조건 | 결과 |
|---|---|
| `갑` 증거번호 | 원고계 (`plaintiff`) |
| `을` 증거번호 | 피고계 (`defendant`) |
| 그 외 파일명에 `원고`, `채권자`, `신청인`, `항고인` | 원고계 |
| 그 외 파일명에 `피고`, `채무자`, `피신청인`, `상대방` | 피고계 |
| 모두 없음 | 미지정 |

원고계 단어와 피고계 단어가 모두 있으면 현재는 원고계가 우선한다.

## 정렬 규칙

- 일반 문서와 첨부서류: 제출일 오름차순 → 기록순번 오름차순.
- 날짜가 없는 항목은 날짜가 있는 항목 뒤로 보낸다.
- 순번이 없으면 원래 수집 순서를 사용하되, 일반 문서 중 `소장`을 다른 무순번 문서보다 먼저 둔다.
- 서증: `갑/을 + 본번 + 가지번호` 기준 오름차순. 통상 `갑` 묶음 뒤에 `을` 묶음이 온다.
- 증거번호가 없는 서증은 기록순번을 사용하고, 그것도 없으면 뒤쪽의 수집 순서를 사용한다.

## 현재 구현상 주의점

후속 작업자가 아래 동작을 의도된 규칙으로 오해해 복제하지 않도록 한다.

1. 사건번호 끝 숫자를 1~6자리만 허용한다. 코드 주석의 `2024가단5369527`처럼 7자리인 값은 앞 6자리까지만 잘못 추출될 수 있다.
2. 표시용 날짜·문서종류 탐색은 `YYYY.MM.DD`만 허용하지만 정렬은 `2024. 3. 1`도 허용한다. 같은 파일을 표시와 정렬에서 다르게 해석할 수 있다.
3. 상세정보 추출은 ASCII 괄호 `()`만 지원한다. 증거번호 경계는 전각 괄호 `（）`를 일부 허용하지만 그 안의 문서명 추출은 일관되지 않다.
4. 서증 정렬에서 `을`의 기준 오프셋이 `100000`이다. 갑호증 본번이 1001 이상이면 일부 을호증 뒤로 갈 수 있다.
5. 로컬 파일 수집 결과를 먼저 정렬하지 않는다. 날짜·순번이 모두 없는 동률 항목의 순서는 파일시스템 열거 순서에 의존한다.
6. 날짜는 형식만 보고 실제 달력상 유효성은 검사하지 않는다.
7. `갑 1`처럼 `호증`이 없는 짧은 표현도 증거번호로 인정하므로 일반 문구를 서증으로 오인할 여지가 있다.

## 그대로 전달할 변경 지시문

```text
소송기록 PDF 파일명 파서를 이 핸드오버 문서의 규칙에 맞게 변경하라.

구현 범위는 우선 src/renderer/src/viewer/recordOutline.ts와
scripts/verify-record-outline.mjs 두 파일로 제한한다. 파일 수집 정책을 바꾸는 요구가
아니면 App.tsx, main/index.ts, remoteFs.ts는 수정하지 않는다.

필수 조건:
1. 파일 경로는 변경하지 않고, 파싱할 문자열만 NFC로 정규화한다.
2. 분류 우선순위는 서증 > 첨부서류 > 일반 문서로 유지한다.
3. 개별 PDF 파일명과 합본 PDF 북마크가 같은 분류 함수를 계속 사용하게 한다.
4. 기존 세 가지 서증 회귀 사례를 보존한다.
5. 새 규칙마다 verify-record-outline.mjs에 입력 파일명과 기대 결과를 한 건 이상 추가한다.
6. 새 파서 계층이나 의존성은 만들지 말고 기존 classify 흐름을 최소 수정한다.
7. npm run verify:record-outline과 npm run typecheck를 통과시킨다.

현재 구현상 주의점 1~7은 의도된 계약이 아니다. 변경 요청에서 명시한 항목은
회귀 테스트를 먼저 추가한 뒤 고치고, 명시하지 않은 항목은 별도 리팩터링하지 않는다.
```

## 최소 회귀 사례

현재 반드시 보존해야 하는 사례:

| 파일명 | 기대 범주 | 기대 표시명 |
|---|---|---|
| `2026비합50043_001_2026.06.30_서증_(갑_1_입금내역)_신청인.pdf` | 서증 | `갑1  입금내역` |
| `2026비합50043_002_2026.06.30_서증_(을 제2호증의1 거래내역)_상대방.pdf` | 서증 | `을2-1  거래내역` |
| `2025느합1050_013037_2025.08.13_준비서면_서증_입출금 자료_(을15-1_입출금 자료)_상대방.pdf` | 서증 | `을15-1  입출금 자료` |

후속 변경에는 영향을 받는 일반 문서, 첨부서류, 정렬, 당사자 판정 사례만 추가한다. 별도 테스트 프레임워크는 필요 없다.
